# Kamimusubi Worldview Polish Audit

## 目的

Kamimusubiの体験を「検索」ではなく「相談から意味と出会う体験」として磨くため、Web / Mobile / Backend の文言を監査する。

## 判断軸

- 「検索」ではなく「相談」
- 「神社一覧」ではなく「意味との出会い」
- 「ご利益」ではなく「自分との接点」
- 誕生日・九星・五行・方位は前面に出さず、補助シグナルとして扱う

## 監査対象

- Web表示文言
- Mobile表示文言
- Backend生成文言
- テスト内の期待文言
- docs内のプロダクト説明

# KAMI MUSUBI Worldview Parity Audit

## 結論

Web / Mobileとも「相談テーマチップ」「参拝前の問い」など軸となる語彙は共有できており、土台のトーンは揃っている。一方で、**「候補」という語彙の多用**（Web/Mobile Concierge・Shrine Detail・Map全体で頻出）と、**Ranking / Map画面での集計ロジック・外部サービスの直接的な開示**（月間TOP10説明文、Googleマップ連携文言、スコア集計説明）が、「検索アプリ」「ランキングアプリ」の印象を最も強く残している。またMobile Shrine Detailの英語eyebrowラベル（RECOMMENDATION / CONTEXT / MEANING等）はUIパーツ感を強め、静かで余白のある世界観を損なっている。

もう一つの発見として、**Mobile Homeには「近くの神社」「人気神社ランキング」「検索チップ」用のコンポーネント（NearbyShrines.tsx / RankingCarousel.tsx / PopularSection.tsx / SearchChips.tsx）が実装済みだが、実際にはHome画面のどこからも呼び出されていない**（`apps/mobile/app/index.tsx` は31〜112行のみで完結し、これらをimportしていない）。結果として、Web Homeにある「相談後に地図・一覧・ランキングを補助的に確かめる」導線が、Mobileでは事実上存在しない。これは文言以前の構造的なWeb/Mobile差であり、次の実装判断（接続するか、削除するか）が必要。

総じて、**Concierge画面自体はWeb/Mobileとも「相談ファースト」の世界観を比較的よく体現できている**一方、**Ranking / Map / Shrine Detailの「根拠・集計・外部連携」まわりの文言**に、避けたい印象（検索・一覧・ランキング・断定）が集中している。

## 画面別監査

### 1. Home

- **役割**
  - Web: 相談入力の起点 ＋ 相談後の補助導線（地図・神社一覧・人気ランキング・御朱印フィード）を1画面に集約したハブ。
  - Mobile: 相談入力に特化した起点。実装上、他セクション（近くの神社／ランキング／検索チップ）は画面に接続されていない。

- **現在の問題**
  - Web Home下部に「神社一覧も見る」「地図でも確認する」「ランキング詳細へ」と、相談を経由せず一覧・地図・ランキングへ直接誘導する導線が並び、相談直後に複数の“検索アプリ的入口”が露出する。
  - Web HomeRankingSectionの「最近30日間のスコア（お気に入り数＋閲覧数）で集計しています。」は集計ロジックをそのまま開示しており、「意味との出会い」という軸から外れる。
  - Mobile Hero文言自体は世界観に忠実だが、`SearchChips.tsx`（地域「東京都」「京都府」、ご利益「縁結び」「厄除け」等、混雑「空いている」、所要時間「30分以内」）は完全に検索アプリのファセットUIであり、将来接続されると世界観を大きく壊すリスクがある。
  - Web/MobileでHome CTA文言が不一致（Web「この相談ではじめる」／Mobile「この相談からご縁を見る」）。

- **残すべき要素**
  - 6つの相談テーマチップ（疲れを整えたい／迷いを整理したい／前に進みたい／静かに考えたい／人との縁を見直したい／仕事の流れを整えたい）はWeb/Mobile完全一致しており、世界観の軸として機能している。
  - Mobile Heroの「今の相談を、神社とのご縁につなげる」「ここでは相談内容だけを整えます。次の画面で、今の相談から結ばれた神社を確認できます。」は相談ファーストの理想形。

- **修正候補**（詳細は文言置き換え表）
  - Web HomeRankingSectionの集計説明文を静かな文脈コピーへ置き換え
  - Home CTA文言をWeb/Mobileで統一
  - Mobileの未接続コンポーネント（SearchChips等）の扱いを意思決定（保留事項参照）

- **優先度**: A（Web Rankingセクションの数値露出文言）／B（Home CTA統一、未接続コンポーネントの方針決定）

### 2. Concierge

- **役割**
  - KAMI MUSUBIの中核体験。相談入力 → 推薦 → 根拠説明 → 行動提案 → 保存という一連の「意味との出会い」を担う唯一の画面。

- **現在の問題**
  - 推薦根拠の見出しがWeb/Mobileで不一致。Web「相談から見た意味」「この神社が持つ文脈」に対し、Mobile「今の相談とのつながり」「根拠として見ている情報」。特にMobileの「根拠として見ている情報」は「神社固有の文脈」「ご利益・意味」「参拝との相性」「行きやすさ」「参考情報」という5分類の機械的な列挙で、"検索結果の絞り込み根拠表示"に近い見え方になっている。
  - Mobile条件レイヤーは「誕生日」「参拝スタイル」「ご利益」を相談画面内に常設展開しており、ラベル＋ピル選択肢の並びが完全にフィルターフォームに見える。Webは「希望を補足する」パネルとして折りたたみ式にしており、相談本文が主役であることを保っている。
  - Web「信頼できる神社候補」という眉ラベルは、"信頼できる"という断定的なお墨付き感があり、「占いっぽく断定する」に抵触しうる。
  - 「候補」という単語がWeb/Mobile問わず極めて高頻度（「他の候補」「次の候補」「信頼できる神社候補」「相性から見た候補」等）。「候補を並べるだけ」という避けたい印象に直結する最重要語彙。
  - Web v3行動CTA「試してみる」「完了」はタスク管理アプリ的で、静けさ・余白のある体験からやや外れる。

- **残すべき要素**
  - 「相談テーマ」「参拝スタイル」「ご利益」という見出し語彙はWeb/Mobile一致しており良い。
  - 「参拝前の問い」はWeb/Mobile一致しており、大事にしたい軸を体現できている。強く維持すべき。
  - ConciergeEntryCard「相談から、向かう神社を見つける」は理想的な見出し。
  - Mobile「今の相談から結ばれた神社」という"結ぶ"の語彙はKAMI MUSUBIらしく残すべき。

- **修正候補**: 文言置き換え表参照

- **優先度**: A（「候補」語彙の全面見直し、Web「信頼できる神社候補」）／B（推薦根拠見出しのWeb/Mobile統一）／C（Mobile条件レイヤーの折りたたみUI化）

### 3. Shrine Detail

- **役割**
  - 推薦判断の根拠を深掘りし、参拝前の問い・参拝後の振り返りへつなげる、相談の続きを担う画面。

- **現在の問題**
  - Mobileは「RECOMMENDATION」「CONTEXT」「MEANING」「EXPLANATION」「NEXT ACTION」「REFLECTION」という英語eyebrowラベルを多用しており、全て日本語見出しのWebと世界観が大きくズレている。英語ラベルの羅列は"UIパーツ感"を強め、静かで余白のある日本語の世界観を損なう。
  - Mobile「選定のポイント」カードは「神社固有の文脈」「ご利益・意味」「参拝との相性」「行きやすさ」「参考情報」「判断材料」「推薦の文脈」というラベル＋値の一覧表示で、Concierge同様「検索エンジンのスコア内訳」的な見え方になっている。
  - Web/Mobile共通のデフォルトフォールバック文言「今の状態と相性が良い候補です。」は「候補」語彙に加え、どの神社にも言えてしまう抽象文。
  - Web「ご利益情報は準備中です。」は情報不足を露呈するエラーっぽい文言で、静けさのある世界観とズレる。
  - 参拝記録・振り返り導線の実装粒度がWeb/Mobileで大きく異なる。Webは参拝直後に即時振り返りプロンプトを表示し「前回との違い」セクションで継続性を示すが、Mobileは`/records`へのリンクのみでその場での振り返り入力導線がない。「行動と振り返り」という大事にしたい体験の核であり、機能差として別途対応が必要。

- **残すべき要素**
  - 直近PR（f22b201b）で追加された「今回の相談の整理」「神社との意味の接続」カードは、この監査が目指す方向性（相談文脈をShrine Detailへ引き継ぐ）を体現しており高く評価できる。日本語タイトル自体は良く、問題は英語eyebrowのみ。
  - Web「あなたの参拝が記録されました。次回の相談で前回の行動として振り返ることができます。」は「行動と振り返り」の軸を体現する良いコピーで、Mobileにも同思想の文言を持たせたい。
  - 「参拝前の問い」はShrine Detailでも一貫しており良い。

- **修正候補**: 文言置き換え表参照

- **優先度**: A（Mobile英語eyebrowラベルの日本語化）／B（Web/Mobile共通の抽象フォールバック文言の見直し、Mobile振り返り入力導線の実装）

### 4. Map

- **役割**
  - Web: 「相談のあとに、距離や周辺を補助的に確認する」独立ページ（`/map`）。
  - Mobile: 専用画面が実質存在しない。Home用に`NearbyShrines.tsx`が実装されているが未接続（「1. Home」参照）。Shrine Detail内の「地図で経路を確認する」ボタン（外部地図アプリ起動と推測）のみが地図的機能。

- **現在の問題**
  - Mobileには地図画面もNearby一覧も実質的に存在しない。Web/Mobileで「近さを確かめる」という体験の有無自体が大きく乖離しており、これは文言以前の機能パリティ問題。
  - Web Mapページの「Googleマップで探す」「Googleマップで見る」「経路案内」は外部サービスへの丸投げ感が強く、KAMI MUSUBI独自の"意味との接続"がこの画面には一切なく、避けたい印象（検索・一覧・候補）が最も色濃く残っている（「近くの候補が見つかりませんでした。」「おすすめ（起点）」等）。
  - 「情報の取得に失敗しました。」等、Conciergeの丁寧な文言と比べてMap画面はテンプレート的・機械的な文言が多く、画面ごとの世界観の温度差が大きい。

- **残すべき要素**
  - Web Mapページ冒頭の「近くの神社」「今いる場所から、静かにたどれます。」という導入コピーは"押しつけない・静かな"世界観に合っている。このトーンをリスト部分にも波及させる方向が良い。

- **修正候補**: 文言置き換え表参照

- **優先度**: A（Web Map内の「候補」「おすすめ（起点）」等の検索的文言）／B（MobileにMap機能を持たせるか、Shrine Detail内の経路確認のみに留めるかの意思決定）／C（Google Maps連携文言のトーン調整）

### 5. Ranking / 一覧系

- **役割**
  - Web: 「近くの人気神社／月間TOP10／年間TOP10」の3タブで人気を可視化するページ（`/ranking`）。神社一覧（`/shrines`）は検索寄りの探索ページ。
  - Mobile: ボトムタブに直接は出ない補助画面（`href: null`）。お気に入り数でソートした単純リストのみ。

- **現在の問題**
  - Web Rankingの「月間TOP10は直近30日間の人気、年間TOP10は過去1年分のデータを元にしたランキングです。」は集計ロジックをそのまま開示しており、「人気ランキング中心」という避けたい印象そのもの。🥇🥈🥉の絵文字と合わせ、一般的なランキングアプリの見た目・語り口になっている。
  - Web「神社一覧も見る」「神社一覧」「神社を探すへ戻る」という文言・`/shrines`一覧ページの構造自体が"検索アプリ"の一覧ページであり、相談を経由しない探索チャネルとして意図的に切り離されているように見える。
  - Mobile Rankingの「保存数の多い神社を、参拝先選びの補助として見られます。」は「補助」という位置づけを明示しておりWebより世界観への配慮があるが、「★4.3　♡12」のような数値表記はランキングアプリ的な即物性が強い。
  - Web/MobileでRanking機能の粒度が大きく異なる（Web: 3タブ＋現在地連動、Mobile: シンプル1リスト＋お気に入りフィルタのみ）。「Rankingは補助であり主役ではない」というMobile側の姿勢は良いが、明文化されたルールではなく偶発的な実装差の可能性が高い。

- **残すべき要素**
  - Mobile「保存数の多い神社を、参拝先選びの補助として見られます。」はランキングを"補助"と明言しておりKAMI MUSUBIらしい距離の取り方。Web側もこのトーンに揃えるべき。

- **修正候補**: 文言置き換え表参照

- **優先度**: A（Web Rankingの集計ロジック開示文言・絵文字表現）／B（Web/Mobile Rankingの「補助」ポジショニングの統一）／C（`/shrines`一覧ページ全体の再設計）

## Web / Mobile 統一ルール

- **完全一致させるもの**
  - 相談テーマ6チップの文言（疲れを整えたい／迷いを整理したい／前に進みたい／静かに考えたい／人との縁を見直したい／仕事の流れを整えたい）
  - 「参拝前の問い」という語彙
  - Home CTA文言（「この相談からご縁を見る」に統一）
  - Concierge内の見出し語彙（「相談テーマ」「参拝スタイル」「ご利益」）
  - 「候補」を避け断定しない語り口というトーン＆マナー原則

- **Mobile優先で設計するもの**
  - 情報密度・カード数（Mobileの1画面完結型カード構成を正とし、Webがこれに寄せる方向を検討する）
  - 条件レイヤーの折りたたみUI（Mobile Conciergeは現状展開しすぎのため、Webの折りたたみパターンを逆輸入する）
  - ボトムナビゲーションの「相談を中央に置く」思想（既にMobileが正）

- **Webで情報量を補うもの**
  - Ranking（月間／年間TOP10、現在地連動）などの探索的機能はWebが担い、Mobileは「保存数による補助リスト」に留める
  - Map（Google Maps連携、詳細な近隣リスト）はWebが主、Mobileは「地図で経路を確認する」程度の軽い導線に留める
  - 過去相談との比較（state delta）、Premiumでの変化の振り返りなど情報量の多い機能はWeb/Premiumを正本にする

- **Backend生成文言として正本化するもの**
  - 推薦理由（recommendation_reason_v4）、行動提案（action_suggestion_v4）、reasonFacts、shrineMeaning／actionMeaning／consultationSummaryは、過去監査（mobile-web-concierge-ui-quality.md）で既にBackend/Webが正本という整理がされている。これを踏襲し、Mobileはこれらを「表示するだけ」にし、独自に類似文言を生成しない
  - eyebrowなどのUI装飾ラベルはBackendではなくクライアント表示レイヤーの責務とし、日本語で統一する
