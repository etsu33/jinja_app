# 監査文書の更新運用方針

## 目的

同一の監査文書を複数の実装PRが並行して更新する際に発生し得る、squash mergeによる内容消失を防ぐ。

---

## インシデントの記録（本方針の根拠）

2026-07-18、以下の経緯で`docs/audit/legacy-settings-remediation-plan.md`の内容が一部消失した。

1. PR #2080（`token.ts`削除）が、`legacy-settings-remediation-plan.md`の#10行・PR-B「対象」行・「#10の実施状況」段落・「実施順序」該当箇所を更新し、さらにファイル末尾へ新セクション「## 13. #10の追加対応（PR #2080）」を追加してマージされた
2. PR #2081（Mobile Home Component群削除）は、PR #2080がマージされる**前**の`develop`から分岐したブランチで作業しており、同じファイルの#6関連箇所を更新し、同じくファイル末尾へ新セクション「## 13. #6の追加対応（PR #2081）」を追加した
3. PR #2081がPR #2080より後にマージされた際、squash mergeの結果、PR #2080が追加した内容（#10行の修正・PR-B節の修正・「## 13. #10の追加対応」セクション全体）が`develop`上から失われ、PR #2081側の内容のみが残った
4. PR #2080のコード変更（`token.ts`削除）自体はGit履歴・`develop`に正しく反映されていたため、実装への影響は無かった。影響を受けたのは監査文書の記述のみだった
5. 後続の作業（候補#23の監査PR）で`develop`最新化時にこの消失を発見し、PR #2080のコミット（`7a642f68`）を`git show`で確認した上で、失われた内容を復元した

**根本原因**: 2つのPRが、同一ファイルの同一箇所（末尾）へ、共通の祖先を持たない状態で並行して追記したため、squash merge（またはrebase merge）が3-way mergeとして正しく機能せず、後発PRの内容が先発PRの内容を上書きした。

---

## 方針

### 1. 同一監査文書を複数の実装PRで並行更新しない

`legacy-settings-final-audit.md`・`legacy-settings-remediation-plan.md`のような共有トラッキング文書は、複数の実装PRが同時にOPENな状態で並行更新しない。ある実装PRがこれらの文書を更新中（ブランチ上で編集中、またはOPENなPRとして未マージ）の間は、別の実装PRを新たに同じ文書に対して起票しない。

やむを得ず並行が発生した場合（例: 既にOPENなPRの存在に気付かず着手してしまった場合）は、後発PRのマージ前に4節の手順で対応する。

### 2. 実装PRではコードと対象固有文書のみを変更する

コード削除・依存整理などの実装PRは、以下のみを変更範囲とする。

- 実装コード（Backend/Web/Mobile）
- その実装PR固有の新規ドキュメント（例: `docs/audit/backend-origin-env-migration-design.md`のような、他のPRと競合しない単独の監査・設計文書）

`legacy-settings-final-audit.md`・`legacy-settings-remediation-plan.md`のような共有トラッキング文書は、実装PRでは**変更しない**。これにより、実装PR同士が同じ文書を取り合う状況自体を発生させない。

### 3. 複数PR完了後に監査文書更新専用PRを作成する

複数の実装PRがマージされた後、それらの結果をまとめて反映する「監査文書更新専用PR」を別途作成する。この専用PRの中では、`develop`上でマージ済みの各実装PRの内容を`git merge-base --is-ancestor`等で確認し、削除対象の残存参照を再検索した上で、共有トラッキング文書を更新する。

この専用PRが唯一、共有トラッキング文書を変更する権利を持つ。専用PR自体も、2節の原則に従い並行させない（1つの専用PRが完了してから次の専用PRに着手する）。

### 4. 監査文書を変更するPRはマージ直前にorigin/developを取り込む

共有トラッキング文書を変更するPR（3節の専用PR）は、マージボタンを押す直前に`git fetch origin && git rebase origin/develop`（またはマージ）を実行し、他のPRが並行してマージされていないかを確認する。並行マージが検出された場合、その内容を取り込んだ上で自分の変更を再構成してからマージする。

### 5. squash merge後に対象文書の追記内容が残っていることを確認する

マージ完了後、`develop`をpullし直し、`grep`等で自分が追加・修正した内容が実際にファイル上に残っていることを確認する。特に、複数のセクション番号（`## 13`、`## 14`等）が意図した順序・内容で存在するかを確認する。消失が発見された場合は、7節の手順で復元する。

### 6. 競合が起きやすい末尾追記ではなく項目番号単位で更新する

新しいセクションをファイル末尾へ追加する形式の更新は、複数PRが同じ挿入位置（末尾の直前行）をアンカーとして取り合うため、squash mergeでの上書き衝突が起きやすい。

可能な限り、以下を優先する。

- 各PRは自分が担当する項目番号（例: #10、#6、#23）に対応する**既存の行・既存のセクション内**をピンポイントで編集する
- 新規セクションの追加がどうしても必要な場合は、末尾ではなく、関連する既存セクション（例: 該当項目のPR-A〜PR-Fセクション直下）に挿入し、複数PRが同じ挿入位置を取り合わないようにする
- やむを得ず末尾に新規セクションを追加する場合は、2節の原則（実装PRでは触らない、専用PRのみが触る）を徹底し、専用PR同士も並行させない

### 7. 復元が必要になった場合はGit履歴とPR本文を根拠にする

内容消失が発覚した場合、復元する内容はGit履歴（`git show <消失したPRのコミットハッシュ>`）と、当該PRのPR本文（GitHub上の説明文）を正本として復元する。記憶や推測で復元しない。

復元後は、本方針のインシデント記録（上記）と同様に、消失の経緯・原因・復元根拠を復元先の文書自体に明記し、再発時の調査を容易にする。

## 適用範囲

本方針は、以下の複数PRから参照・更新される共有トラッキング文書に適用する。

- `docs/audit/legacy-settings-final-audit.md`
- `docs/audit/legacy-settings-remediation-plan.md`

同様の性質を持つ他の監査文書（複数の実装PRから継続的に更新されることが見込まれる文書）が今後生まれた場合も、本方針に準拠する。

単独の実装PRのみが参照する個別の監査・設計文書（例: `docs/audit/backend-origin-env-migration-design.md`）は、他PRとの並行更新リスクが無いため、本方針の主要な対象ではない。
