## 5. Step 5 — 既存 `Source` 概念の性格

### 5.1 事実

- **モデル名・フィールド構成は汎用的である。**
  名前は `ShrineKnowledgeSource` であって特定Fact種別に紐づく命名ではない。
  `source_type` の10値（公式 / 行政 / 文化財 / 学術 / 博物館・文書館 / 郷土史 /
  観光公式 / 二次編集 / 現地観察 / 内部調査）は特定の項目種別を前提としない
  一般的な出典分類であり、`title` / `publisher` / `url` / `bibliography` /
  `accessed_at` / `language` は一般的な書誌フィールドである。
- **Sourceモデル自身は接続先を持たない。**
  紐づけは常に相手側（`ShrineDeity.sources` / `ShrineHistory.sources`）の
  M2Mとして定義されており、`ShrineKnowledgeSource` にはターゲットを限定する
  FKもgeneric relationも存在しない。
- **一方、docstring・正本文書・実際の利用箇所はすべてFact Layer限定である。**
  - モデルdocstring: 「神社Knowledge（ShrineDeity / ShrineHistory）の出典」
  - 正本: `docs/knowledge/shrine-knowledge-contract.md`「Source契約」。同書の
    対象範囲は `deity` / `shrine_history` の値の意味・出典・確認状態・信頼度
  - 実装上の接続点は2つ（Deity / History）のみ
  - `verification_status` / `confidence` の運用意味は
    `services/evidence_gate.py` の Fact usable 判定として定義されており、
    Fact Layer の文脈でのみ解釈が確定している

### 5.2 「history_theme由来の出典管理か」という点についての事実訂正

タスク設問が例示した「history_theme由来の出典管理」という仮説は、
**実測に合致しない**。`ShrineKnowledgeSource` は `history_theme` とは一切
接続しておらず、由来は Fact Layer（`deity` / `shrine_history`）の
Knowledge Model Foundation（PR #2221）である。
`history_theme` に Evidence を持たせる作業（`HistoryThemeAssignment`）は
その約1ヶ月後のPR-F2（#2675）であり、**そこでは `ShrineKnowledgeSource` は
一切参照されていない**。

### 5.3 どちらの解釈も成り立つ

以下の理由により、**「汎用的な出典管理の仕組み」と「特定タスク限定の仕組み」の
どちらの解釈も現状の事実から成立する**。本書は、PR-F4がこれをそのまま拡張して
使うべきか、別概念として並走させるべきかを判断しない。

| 解釈 | それを支持する事実 |
|---|---|
| **汎用として作られた** | モデル名・フィールド構成が特定Fact種別に依存しない／Source側にターゲット限定のFKがなく、新しい紐づけ元を追加してもSourceのスキーマ変更が不要な構造／`source_type` 10値が神社Knowledge一般をカバーする分類になっている |
| **特定タスク限定として作られた** | docstringが接続先を `ShrineDeity` / `ShrineHistory` と明示／正本文書 `shrine-knowledge-contract.md` の対象範囲が `deity` / `shrine_history` に限定されている／実接続点が2つのみ／import・export・coverage・evidence_gate・selector のすべてがSourceを「Factの付属物」として扱っている／`verification_status` / `confidence` の運用意味がFact usable判定として定義済みで、Assignment文脈での意味は未定義 |

## 6. 盲点・反証（本監査が確認していないこと）

1. **「Qualificationは実装済み」と言えるかは、粒度によって答えが反転する。**
