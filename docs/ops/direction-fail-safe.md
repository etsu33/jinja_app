# 方位機能の縮退契約と障害対応

## 原則

方位は相談内容とご利益を中心にした推薦の補助情報である。方位関連処理の失敗を、相談API、通常推薦、通常理由、候補閲覧の失敗へ昇格させない。クライアントは方位を再計算・補完せず、共通契約で妥当な `direction_reference` だけを表示する。

## 共通縮退契約

| 障害 | 継続する機能 | 省略する機能 | 利用者への状態 |
| --- | --- | --- | --- |
| ジオコードの500・タイムアウト | 相談、地点なしの通常推薦、別方式の選択 | 手動地点の確定 | 検索失敗を読み上げ、方位無効化などを選べる |
| 方位プロフィール計算失敗 | 相談、通常推薦、通常理由 | 方位加点、方位カード | 通常結果のみ表示 |
| 1候補の方位計算失敗 | 他の全候補、当該候補の通常理由 | 当該候補の方位加点・カード | 通常候補として表示 |
| 不正な `direction_reference` | 候補、詳細、通常理由 | 不正な方位情報と方位分析イベント | 方位カードを表示しない |
| 分析送信失敗 | 表示、クリック、相談、外部遷移 | 分析記録 | 操作を遅延・中断しない |
| 不正・利用不能な地図URL | 候補閲覧、詳細閲覧 | 経路遷移 | 「経路リンクを利用できません」と表示 |

`calculation_method` は `annual_monthly_kyusei_v1` のみを受理する。未知の方式は将来値であっても推測せず省略する。日盤・時盤や固定ダミー方位へ置き換えない。

## 障害ログ契約

許可するのは固定イベントコードとリクエスト相関IDだけである。

- `profile_calculation_failed`
- `direction_score_candidate_failed`
- `direction_reference_candidate_failed`
- `enrichment_failed`
- `direction_analytics_delivery_failed`

座標、住所、駅名、都道府県名、神社情報、生年月日、参拝日、相談文、推薦理由、例外メッセージ、イベントpayloadを記録しない。スタックトレースに入力値が含まれ得るため、この境界では例外本文も記録しない。

## 障害調査手順

1. 通常相談と候補表示が成功しているか確認する。
2. 固定コード別の件数、開始時刻、Web／モバイル、リリース版を確認する。
3. `direction_reference` の表示率と方位加点率が同時に低下しているか確認する。
4. 個別ユーザーの入力値を収集せず、固定fixtureで再現する。
5. Backendならプロフィール計算、候補スコア、レスポンス付与のどの境界か切り分ける。
6. クライアントなら不正レスポンス、分析provider、地図URL、ジオコードを個別に故障注入する。
7. 方位を無効化した通常相談が成功しない場合は、方位以外の障害として別途エスカレーションする。

## リリース前チェックリスト

- [ ] 方位計算例外でも相談APIが200を返す
- [ ] 1候補の失敗で他候補が失われない
- [ ] 方位加点が0になり、通常理由が維持される
- [ ] malformed／未知方式の方位カードが表示されない
- [ ] ジオコード500・タイムアウト後も方位無効化で相談できる
- [ ] 分析例外がクリックと遷移を妨げない
- [ ] 不正な地図URLが代替表示になる
- [ ] 障害ログと分析payloadに禁止情報がない
- [ ] Backend、Web、モバイルの型・回帰・E2E検査が成功する
- [ ] 新しい監視サービス、日盤・時盤、ダミー方位が追加されていない
